# Task: local share / zip as a source for TSConf over the ZiFi UART

**Status: BUILT AND BOARD-VERIFIED (2026-11-13). The FUSE virtual-FAT route is implemented as `tools/tsshare` (branch `tsshare`; results: `tools/tsshare/docs/BOARD.md`, `tools/tsshare/docs/PERF.md`). The text below is the spike-era analysis and rationale.**

**Update after spike D (owner prefers NOT to alter Main_MiSTer):** the Minimig and ao486 shares are *not* virtual disks. Each is a filesystem RPC served by Main_MiSTer (`support/minimig/minimig_share.cpp`, ~930 lines; `support/x86/x86_share.cpp`, ~1200 lines) over a DDR mailbox (ARM mmaps `/dev/mem`: 8 KB at `0x27FF4000` for Minimig, `0x300CE000` for x86; the ARM polls a request word with a magic number and echoes an ack), with a guest-side driver on the Amiga/DOS side. The core-specific part in Main_MiSTer is tiny (an `is_minimig()` gate and a poll call). There is no generic mechanism for a core to trigger ARM code: UIO opcodes are ARM-initiated, `/dev/MiSTer_cmd` accepts only `fb_cmd`, `video_mode`, `load_core`, `screenshot`, `volume`, and `user_io_file_mount` mounts exactly one regular file (no folder, no zip). So a clean "folder as drive" needs a new `tsconf_share.cpp` in Main_MiSTer; without editing Main the realistic design is the same RPC-over-DDR-mailbox idea with a separate ARM daemon (option B below) or the UART daemon (option A).

**Verdict after the WC source check (spike C):** a ZiFi plugin cannot make a share behave like a local folder for third-party player plugins. Use it to *sync* a folder into a cache directory on card 1, then browse and play normally. For a share that acts as a real drive (open folder, play, auto-next), the virtual FAT volume on card 2 (Main_MiSTer change) is the only route that works without per-track gaps or user keypresses.

## Goal
Browse and fetch files from a folder or zip on the MiSTer's Linux side from a Wild Commander (WC) plugin, over the core's existing ZiFi UART, and open the result transparently. No new SD path.

## What the spike found
Full notes (with citations) are in `docs/spikes/share-A-uart-rtl.md` (core UART RTL), `share-B-zifi-midilink-wc.md` (ZiFi, MiSTer UART, WC plugin API, prior art) and `share-C-wc-plugin-launch.md` (WC plugin hand-off and next-file behaviour) and `share-D-main-mister-shares.md` (how Main_MiSTer serves the Minimig/ao486 shares, and options without editing it). They were written by research agents from public sources and are unverified secondary notes. The facts that matter:

- **The core already has ZiFi.** `rtl/periph/zifi.v` implements the HackerVBI/ZX-Evo ZiFi FIFO ports (`#BFEF` data, `#C7EF` cmd/err, `#C0EF` RX used, `#C1EF` TX free; RS232 variant `#C2EF/#C3EF`). RX FIFO 8192 B, TX FIFO 256 B, polling only (no Z80 interrupts), no flow control (`UART_RTS/DTR` tied low, CTS/DSR ignored), fixed 115200 baud (`CLKS_PER_BIT = 28_000_000/115200 = 243`, `zifi.v:227,241`).
- **UzixLS/ZiFi is a Z80 client program, not hardware.** It already downloads files over HTTP on TSConf (zxart, vtrdos, ...). Its README documents the MiSTer setup: OSD *UART Connection = Modem, Link = TCP, 115200*; ZiFi then speaks Hayes (`ATTEL0`, `ATTRANS0`, `ATQ0`, `ATDT<host>:80`) followed by raw HTTP/1.1. HTTP only, no TLS.
- **MiSTer already bridges the UART.** Main_MiSTer `SetUARTMode()` runs `/media/fat/linux/uartmode <mode>` on every mode change; Modem mode (4) starts `midilink` (MidiLink_MiSTer), a Hayes-over-TCP emulator on `/dev/ttyS1`. Its OSD baud list tops out at 115200. No ESP8266-AT emulator exists in MiSTer.
- **Wild Commander plugins** are Z80 assembly `.WMF` files (API v13, `pentevo/soft/WC/source/plugins/READ_ME.TXT` in tslabs/zx-evo). A plugin can create files in the current WC directory (`MKfile` + `SAVE512`) and ask WC to reread the directory (exit code 3). Opening a `.trd` is done by WC through the mounter plugin by extension. Whether a plugin can launch another plugin or file programmatically is **unconfirmed**. No networking WC plugin exists. A plugin must talk to the ZiFi ports itself.
- **WC source check (spike C, tslabs/zx-evo `pentevo/soft/WC`):**
  - **No hand-off.** A plugin cannot start another plugin or open a file by name: the 87-entry function table has no such call, exit codes stop at 4, and exit 3 (reread directory) returns A=0 and ends any next-file chain. No key injection either (WC reads the PS/2 driver directly).
  - **Next/prev (exit 2/4).** WC moves the active panel's cursor one entry and re-dispatches by the new file's extension. Directories stop the chain; a file with no matching plugin opens the viewer menu; at the last entry WC reopens the same file (the plugin must check HL'=DE'). The panel is a RAM listing built at directory read, so a file created by MKfile is invisible until an exit-3 reread.
  - **Extensions.** 32 slots of 3 characters; the extension is the last 3 characters after the final dot, capitalised (`TRACK.PT3.LNK` routes as `LNK`).
  - **State and writes.** Plugins stay resident, and header pages that are never touched keep data between runs (page count fixed in the header). No truncate/overwrite: use DelFl, then MKfile with the real size, then SAVE512.
  - **Unconfirmed.** READ_ME says API #13 but the code accepts up to #12; whether SAVE512 can grow an existing file; exit 4 at the top of the list.
- **Reported, to verify:** `zifi.v:199` computes TX free as `8'h255 - usedw` (that is 85, not 255, so wrong once more than 85 bytes are queued), and an `rx_busy` workaround makes the RX count read 0 for a while after each received byte (`zifi.v:153-162`). Both would hurt throughput.

## Proposed stages
0. **No code, 1 hour.** Run a static HTTP server on the board over a test folder (BusyBox `httpd` if present, else any tiny server), set TSConf's OSD UART to Modem/TCP/115200 and use the existing ZiFi client with `ATDT127.0.0.1:80`. Proves the path end-to-end and gives a speed number. Needs no change to `uartmode` or any other core's files.
1. **WC plugin** `SHARE.WMF`: *folder sync*. List the server's index, download the whole folder (or a chosen subset) with a progress bar into a cache directory on card 1 (DelFl + MKfile + SAVE512), return exit code 3. The user then opens the cache folder and plays or browses as with any local folder, auto-next included. Per-track on-demand download does not work: a placeholder routed to our plugin cannot hand off to the player (no launch call), and a placeholder with the player's own extension would just feed the player an empty file. Zip support is server-side: a tiny daemon unzips on demand, so the Z80 never sees zip. Sync time is folder size over link speed (module/`.pt3` folders are a few MB: about 5 minutes at 115200, well under a minute at 1 Mbaud).
1b. **Alternative to stage 1: virtual FAT on card 2.** Main_MiSTer presents the share as a read-only FAT volume in the second VHD slot built by the dual-VHD work. WC sees a normal drive, so folders, players and auto-next work with no sync and no Z80 code. Cost: a C++ change in Main_MiSTer (virtual FAT builder, lazy file reads, a way to pick a folder for the slot); the folder must not change while mounted. Choose 1 or 1b by whether the sync wait is acceptable.
2. **Speed.** Make `CLKS_PER_BIT` selectable (1 Mbaud = 28 clocks, 2 Mbaud = 14, both exact; 921600 is 1.3 % off). Fix the two ZiFi bugs above without breaking `zifi.spg`. Replace MidiLink's Modem mode with a small purpose-built daemon on `/dev/ttyS1` (MidiLink's list caps at 115200, and no flow control means the daemon must pace itself). Estimate: 115200 gives about 11 KB/s, so a 640 KB `.trd` takes about a minute; 1 Mbaud is about 10x faster if the Z80 poll loop keeps up.
3. **Optional:** upload (write back to the share), directory navigation, cache.

## Options that do not edit Main_MiSTer (spike D, ranked by effort)
- **A. UART daemon**: a process on `/dev/ttyS1` answering as modem/ESP. About 300-600 lines plus the Z80 client. Slow (about 11 KB/s at 115200). Needs starting (see below).
- **B. DDR mailbox**: copy the Minimig/x86 transport. The core gets a small DDR master and Z80 ports; a daemon mmaps `/dev/mem` at a free physical range and serves a catalog plus file data. Fast (about 0.5 MB/s on the Z80 side), no AT/HTTP layer. Needs RTL work, the plugin (a WC plugin is the "driver"), and a free DDR range (unconfirmed which).
- **C. Image builder: REJECTED by the owner (2026-11-13).** A script builds a FAT/TRD image from a folder and mounts it in the second VHD slot. It works with every player, but it is a snapshot, needs space equal to the folder (10+ GB, thousands of files is unrealistic), and zips would have to be unpacked first.
- **D. FUSE virtual FAT (preferred if the kernel allows).** Main_MiSTer mounts a VHD by opening a plain file and pread-ing blocks (`user_io_file_mount`). If that file sits on a FUSE mount, a user-space daemon can synthesize the FAT volume lazily: directory structure from the folder tree, file clusters read from the real file or decompressed from the zip on demand, a sparse 16 GB+ virtual disk. WC, players and auto-next see an ordinary drive; huge folders and zips work; Main_MiSTer is untouched. The daemon is started by hand (Scripts menu). **FUSE spike result (2026-11-13, `spikes/fuse-vhd/RESULTS.md`): GO.** Main_MiSTer mounts a FUSE-served file from the OSD picker as SD image 2; WC lists it, real `.trd`/`.spg`/`.vgm` files open and run; a 50 ms-per-read source is tolerated (owner: "little delay at start"). Core reads are serial, at most 16 KB, at arbitrary offsets, median 43 us from the backing file. The OSD picker can reach `_Other`. A virtual-FAT generator must therefore answer any aligned range in well under 50 ms. Sketch for the real daemon (Go, static armv7, about 600-1000 lines, estimate): build FAT32 geometry for a sparse disk (16 GB+, 4 KB clusters, FAT about 16 MB computed lazily), scan the folder tree at start (or on SIGHUP) into an in-memory directory model with long file names (WC shows LFN) and 8.3 aliases, map clusters to file extents, serve data by `pread`, and for zips decompress an entry into a small LRU cache on first access. Measured amplification: a 3.1 MB contiguous file produced 885 requests (8.05 MB requested, overlapping and not page-aligned), so the daemon needs its own read-ahead window cache (see `spikes/fuse-vhd/RESULTS.md`), or a 50 ms source makes a 3 MB demo take about a minute to start. Still to design: 8.3 alias collisions, change handling (re-scan then remount), memory on a 491 MB board for thousands of files, and daemon start without `user-startup.sh` (Scripts menu).

**Board check done (2026-11-13, 192.168.1.15, read-only, kernel `6.18.38-MiSTer`): FUSE is available.** `/dev/fuse` exists (crw-rw-rw-), `/proc/filesystems` lists `fuse`, `fuseblk` and `fusectl`, and `/proc/config.gz` has `CONFIG_FUSE_FS=y`, `CONFIG_CUSE=y`, `CONFIG_FUSE_PASSTHROUGH=y`, `CONFIG_FUSE_IO_URING=y`; loop is built in (`CONFIG_BLK_DEV_LOOP=y`), NBD is not. There is no `fusermount` and probably no libfuse, so the daemon must be a static ARM binary that speaks the FUSE protocol on `/dev/fuse` and mounts with `mount(2)` as root (or links libfuse statically). Still unknown: whether the OSD file browser can show a file on the FUSE mount, and the read latency of the first access to a large directory. If there is no FUSE, fall back to B or to the plugin with per-folder fetch.
- **Starting an ARM process without editing Main or `user-startup.sh`:** the MiSTer Scripts menu (my knowledge, unverified in the spike) can launch a script by hand; the `uartmode` hook runs on every UART mode change but lives on the Linux image and is shared with other cores. Unconfirmed: what `uartmode` does exactly, and whether the UART bridge must be stopped first.
- **Clean fix for later:** a TSConf module in Main_MiSTer, about 250-400 lines for a read-only version, by analogy with the two existing modules. Not wanted by the owner for now.
