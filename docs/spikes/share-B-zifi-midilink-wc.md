# Spike B: WC plugin + ZiFi + MiSTer UART (external research)

## 1. ZiFi
- https://github.com/UzixLS/ZiFi is NOT a hardware module. It is a Z80 internet-client program for ZX-Evolution/TSConf (fork of HackerVBI/ZiFi; MiSTer notes added). Sites: vtrdos, zxart, prods.tslabs, hype, pouet, irclogs; downloads games/disks, views SCR, plays AY. Source: zifi.asm, zifi_sts.asm, tsconfig.asm (sjasmplus); dirs _esp, _rs232, _sd, _spg, _src, _Emul, _pt. Prebuilt STS.TRD in repo root. (README: https://raw.githubusercontent.com/UzixLS/ZiFi/master/README.md)
- Hardware-side Z80 view (https://raw.githubusercontent.com/UzixLS/ZiFi/master/_esp/zifi_driver.asm): ZX-Evo "ZiFi" FIFO UART ports: data #BFEF, cmd/err #C7EF, input FIFO used #C0EF, output FIFO free #C1EF (RS232 variant #C2EF/#C3EF). cmd 1=clear in FIFO, 2=clear out FIFO. This is exactly what rtl/periph/zifi.v in our repo already implements (191-byte windows).
- Protocol expected: real ESP8266 AT firmware. Driver sends ATE0, AT+GMR, AT+UART_CUR=115200,8,1,0,3, AT+CWMODE_DEF=1, AT+CIPMUX=0, AT+CWAUTOCONN=0, AT+CWJAP_CUR="ssid","pw", AT+CIPSTA?, AT+CIPSTART="TCP",host,80, AT+CIPSEND=<n> then raw HTTP/1.1 GET, parses "+IPD,<n>:" frames, AT+CIPCLOSE. So AT+UART_CUR IS used (to 115200) in the ESP path; Spectrum-side baud is set by the core, not the ZiFi program.
- MiSTer mode (UzixLS README): OSD UART Connection=Modem, Link=TCP, Baud=115200. ZiFi then speaks Hayes instead of ESP: ATTEL0, ATTRANS0, ATQ0, then ATDT<host>:80 and raw HTTP on the open socket; zifi.ini SSID/password ignored. => a Hayes modem over TCP (MidiLink) already works with ZiFi on TSConf. HTTP only (no TLS) at this level.
- Not confirmed: exact ESP firmware version, whether the fork's Hayes path is in the zifi.asm I did not read line by line.
- Other Spectrum-side ESP tools (non-TSConf): uGoph, netman-zx (nihirash), FTP_Uno (yomboprime) for ZX-Uno UART (ports #143B/#133B, different from ZiFi). Interface 1bis (spectrumcomputing.co.uk/forums/viewtopic.php?p=36692). None target TSConf.

## 2. MiSTer Main_MiSTer UART
Sources: user_io.cpp, menu.cpp (raw.githubusercontent.com/MiSTer-devel/Main_MiSTer/master/). uart.cpp does not exist (404); main.cpp has nothing relevant.
- Modes (menu.cpp config_uart_msg): 0 None, 1 PPP, 2 Console, 3 MIDI, 4 Modem, 5 UDP (hidden), 6 SNI. State is held as marker files /tmp/uartmode1..6 (GetUARTMode).
- SetUARTMode(mode) (user_io.cpp ~1260): sends UIO_SET_UART to FPGA with value (mode==4||mode==5 ? 1 : mode), then 32-bit baud (two spi_w). Writes /tmp/CORENAME, /tmp/RBFNAME, /tmp/UART_SPEED (decimal baud), then runs `system("uartmode <mode>")` (mode 0..6, a single argument; no other args). Env: none special; script reads /tmp/UART_SPEED. So core sees uart_mode==1 for Modem; our TSConf.sv routes uart_out to UART_TXD for uart_mode 1 or 2, so Modem works (a mode-4 check in the FPGA is not needed).
- Hook: script is `uartmode` (lives in /media/fat/linux/uartmode, canonical copy https://raw.githubusercontent.com/MiSTer-devel/MidiLink_MiSTer/master/uartmode). Run on every mode change, including at core load (SetUARTMode(0) then real mode) and after "Reset UART connection". It kill_all()s (rm /tmp/uartmode*, fuser -k /dev/ttyS1) then starts: 1 pppd, 2 agetty ttyS1, 3/4 `midilink MENU QUIET`, 5 `midilink UDP QUIET BAUD $conn_speed`, 6 snid. Users can edit the script to add their own mode-4 handler (we may not touch other cores' files on the board though).
- tty: /dev/ttyS1 (FPGA-bridge 16550-like UART).
- Baud: CONF_STR token `UART<b1>(label):<b2>...` (up to 10) parsed in user_io.cpp ~814 into uart_speeds[]; first entry default (fallback 115200). Used for modes 1/2 (and 4/5 via a fixed list). MIDI token gives midi_speeds. Modem/UDP use hard list mlink_speeds {110,300,600,1200,2400,4800,9600,14400,19200,31250,38400,57600,115200}, so Modem max via OSD = 115200 (default = uart_speeds[0] when no saved choice). Per-core choice saved in uartmode.<CORE>/uartspeed.<CORE>. Our CONF_STR is "UART115200,MIDI;" so only 115200 in PPP/Console. Main_MiSTer itself does not call tcsetattr on ttyS1; MidiLink does (serial2.c set_baud, custom divisor via setserial for 31250; "ttyS1 loses baud setting" comment, main.c ~909). Higher than 115200: not confirmed (serial2_is_valid_rate list not read).
- Existing bridge: MidiLink (https://github.com/MiSTer-devel/MidiLink_MiSTer, modem.c, tcpsock.c, MidiLink.INI) = Hayes modem emulator over TCP, runs in mode 3/4. Commands: AT, ATDT host:port, ATH/+++, ATZ, ATE0/1, ATQ0/1, ATTEL0/1 (telnet), ATTRANS#, ATBAUD#, ATIP, ATDIR (dial book MidiLink.DIR), ATINI, ATMP3, ATMID, ATM*, ATROWS, **ATSZ** (zmodem send via /bin/sz) and **ATRZ** (zmodem receive via /bin/rz), AT&K0/3/4 flow, AT&D0/2. INI per-core sections ([AO486],[C64]...; no [TSCONF] section so defaults). TCP_BAUD default 115200, TCP_TERM_UPLOAD=/media/fat/UPLOAD, TCP_TERM_DOWNLOAD=/media/fat, TCP_FLOW=3 (RTS/CTS). It also listens (TCP_SERVER_PORT=23) as a telnet term. No ESP8266 AT (CWJAP, CIPSTART) emulation found in MidiLink.
- No ESP-AT emulator in MiSTer land found by search. Related generic tools: tcpser (Hayes), zimodem (ESP firmware, has its own PC/ZModem/"wifi modem" features; not checked in depth). A bridge for a "local share/zip" would be new: either a custom `uartmode` handler on ttyS1 or a MidiLink-like process.

## 3. Wild Commander plugins
- Thread https://forum.tslabs.info/viewtopic.php?f=26&t=143 (WC releases; plugins have extension .WMF; F10 plugin menu, F2 user menu from wc.mnu, F4 editor plugin, Shift+Enter viewer menu). Repo: https://github.com/tslabs/zx-evo/tree/master/pentevo/soft/WC (source/, exe/WC_History.txt, WC_todo.txt).
- API doc: https://github.com/tslabs/zx-evo/blob/master/pentevo/soft/WC/source/plugins/READ_ME.TXT (Plug-in system version #13, Russian/English mix). Fetched via raw URL.
- Language: Z80 asm. Examples in source/plugins: PLUG01.ASM (starter), PLUG02/03; wild_player, rom_writer, mounter (vDOS), file_cr, gsplayer, video_pl, bmpview, ilbmview, multigigascreen, tapsna (TAP mount + SNA launch), txt_editor (F4). Third-party: https://github.com/demyanenko-d/VGMPLAY.WMF.
- Format: header with "WildCommanderMDL" at +16, format byte #13, pages allocated, page at #8000, block table (page, size in 512B units), extension list (up to 3x32), name, call-condition, menu texts, INI parameter struct; max 128 KB total. Runs in #8000-#BFFF window; WC resident area at #6000: system vars (#6000 page, #6004 ESC flag, #6005 ENTER flag, #600D cfg, #600E screen height), function entry #6006 (A=function number), table #6026, page-switch helpers #6020/#6028. MNGC_PL(0) page to #C000, MNG0_PL(78) to #0000, MNG8_PL(79) to #8000.
- Entry: CALL #8000, A = trigger: 0 by extension, 1 on load, 2 screensaver, 3 F10 menu, 4 viewer menu, #12 F2, #14 F4. BC=filename ptr, DE:HL file length, IX active panel. Exit codes in A: 0 exit, 1 not recognized, 2/4 next/prev file, 3 reread directory.
- File API (WC fn numbers): FENTRY 59 (find file/dir in active dir), GFILE 62, GDIR 63 (enter dir), GIPAGPL 50 (rewind plugin's file), LOAD512 48 / SAVE512 49 (512-byte block stream), LOADNONE 61, FindNext 58, ADIR 56, MKfile 72, MKdir 73, REName 74, DelFl 75, STREAM 57, UI: PRWOW 1, ISTR 9 (string input), YN 8, PB_PL 82 (progress bar), MEZZ 12. => A plugin CAN create a file (MKfile + SAVE512) in the current WC directory, then reread dir (exit code 3). Mounting is done by separate plugin (mounter, tapsna), so "open .trd after download" = either exit code 3 and let the user press Enter (WC runs the mounter by extension), or not confirmed whether a plugin can invoke another plugin/launch a file programmatically (no such function in the list I saw).
- Not confirmed: whether plugins may access ports directly (yes in principle, Z80 code; only the "conflict flags" bit 0 SD/NGS is mentioned); no WC function for serial/ZiFi; so the plugin must talk to #BFEF/#C7EF itself.
- Prior art for a networking WC plugin: none found.

## Key design hints
- Cheapest path: MidiLink-style Hayes (mode 4, 115200) already works with ZiFi. A new daemon on ttyS1 could implement ATDT -> local file server (a tiny HTTP server on localhost:80 satisfies ZiFi unchanged: ATDT127.0.0.1:80 via MidiLink, then raw HTTP). Alternative: ZMODEM via ATRZ/ATSZ (needs WC-side zmodem; heavy).
- Gap: MidiLink [TSCONF] INI section absent (no custom baud/flow).
